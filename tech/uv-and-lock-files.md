# uv, pip, venv and hash-pinned lock files

## What it is

Python projects use other people's packages from **PyPI**, the public package index. Four things work together here:

- **venv**: a standard-library module that creates a **virtual environment**, a private folder (`.venv/`) with its own Python and its own installed packages, so one project's packages do not collide with another's.
- **pip**: Python's installer. `pip install name` downloads a package into the environment.
- **A lock file**: a text file listing *every* package, at an *exact* version, with a **hash** (a fingerprint) of the file to install. The project's own `pyproject.toml` says "flask 3.1 or newer, below 4"; the lock file says "exactly flask 3.1.3, and the file must hash to this value".
- **uv**: a fast tool from Astral that writes the lock file (`uv pip compile`). It is used by the maintainer to produce the lock files; the people running the project never need it. Local version here: uv 0.11.2.

## Why this repository uses it

A normal `pip install flask` fetches whatever is newest today, and trusts whatever the index serves. Both are supply-chain risks: a new release can contain a compromise, and a file can be swapped. Pinning exact versions makes builds repeatable and auditable, and `--require-hashes` makes pip refuse any file whose hash is not in the lock, so the installed bytes are the ones the maintainer reviewed.

## Where it appears

| Path | What it does |
| --- | --- |
| `requirements.lock` | Runtime dependencies: 18 packages, each with `--hash=sha256:...`. |
| `requirements-dev.lock` | Runtime plus development tools: 83 packages. |
| `Makefile` (`$(STAMP)` rule) | Creates `.venv` and installs from the dev lock with `--require-hashes`. |
| `Dockerfile` | `pip install --require-hashes -r requirements.lock`. |
| `.github/workflows/ci.yml` | `make check` triggers the same install. |
| `pyproject.toml` | The human-written ranges the lock files are compiled from. |

## How it works underneath

1. **Compile**: `uv pip compile pyproject.toml --universal --generate-hashes ...` reads the ranges in `pyproject.toml`, asks the index which versions satisfy them *and* each other's requirements (this is **dependency resolution**), picks one set, and writes it with hashes of every downloadable file for each version.
2. **`--universal`**: produce one lock that works on all operating systems and Python versions in range. Lines may carry markers such as `; implementation_name != 'pypy'`.
3. **Install**: `pip install --require-hashes -r file` turns on strict mode. Every requirement must be `==` pinned and have a hash, and pip checks each download against the hashes before installing. It also refuses packages not named in the file.
4. **`--no-deps`**: do not resolve dependencies again; trust the file.
5. **Editable install** (`-e .`): installs this project as a link to `src/`, so edits take effect without reinstalling.

## Walkthrough of this repository's use

The first lines of `requirements.lock`:

```
# This file was autogenerated by uv via the following command:
#    uv pip compile pyproject.toml --universal --generate-hashes --python-version 3.12 -o requirements.lock
argon2-cffi==25.1.0 \
    --hash=sha256:694ae5cc...e1346c1 \
    --hash=sha256:fdc8b074...d5741
```
`--python-version 3.12` compiles for the oldest Python the project supports. `-o` is the output file. The dev file adds `--extra dev` (include the `dev` optional dependencies). Each package has two or more hashes because a release has several files (one per platform and wheel type). The trailing `\` continues the line.

The install rule in the `Makefile`:

```make
$(STAMP): requirements-dev.lock pyproject.toml
	$(PYTHON) -m venv $(VENV)
	$(VENV)/bin/pip install -q --require-hashes -r requirements-dev.lock
	$(VENV)/bin/pip install -q --no-deps -e .
	touch $@
```
1. Create the environment with the standard library's `venv`.
2. Install every locked package, hash-checked (`-q` is quiet).
3. Install the project itself without touching dependencies: `--no-deps` because step 2 did that, `-e .` editable.
4. Update the stamp file (`tech/make.md`).

In the `Dockerfile`:

```dockerfile
COPY requirements.lock ./
RUN pip install --require-hashes -r requirements.lock
COPY pyproject.toml README.md ./
COPY src ./src
RUN pip install --no-deps .
RUN pip uninstall -y pip setuptools
```
The lock is copied and installed first so Docker's layer cache reuses that slow step until the lock changes; then the project is installed without dependencies; finally the packaging tools are removed from the runtime image (`tech/docker.md`).

How to update a dependency (the maintainer's workflow, not part of `make`): edit the range in `pyproject.toml`, rerun the two `uv pip compile` commands in the headers of the lock files, review the diff, run `make check` and `make audit`.

## Try it yourself

1. See what is installed and from where:
   ```bash
   .venv/bin/pip list | head -20
   ```
   Expect names such as `argon2-cffi`, `Flask`, `gunicorn`, `psycopg`.
2. See hashes in the lock:
   ```bash
   grep -c -- "--hash" requirements.lock
   ```
   Expect `386`: more than the 18 packages, because most packages list several hashes.
3. Watch strict mode refuse an unpinned requirement (this does not install anything because pip stops first):
   ```bash
   printf 'flask\n' > /tmp/loose.txt
   .venv/bin/pip install --require-hashes --dry-run --ignore-installed -r /tmp/loose.txt
   ```
   Expect `ERROR: In --require-hashes mode, all requirements must have their versions pinned with ==.` (`--ignore-installed` makes pip check the file even though Flask is already installed; without it pip may just say "already satisfied".) (Delete `/tmp/loose.txt`.)
4. Recompile without changing the file (needs uv and network):
   ```bash
   uv pip compile pyproject.toml --universal --generate-hashes --python-version 3.12 -o /tmp/requirements.check
   diff /tmp/requirements.check requirements.lock | head
   ```
   Expect no differences, or only newer versions if the index has moved since the lock was written (the header comment line names the output path and may differ).

## Mistakes people make

- Installing from a loose `requirements.txt` in CI and from a different one in Docker. Both use the same lock here.
- Editing a lock file by hand. Always recompile.
- Not committing the lock file. It is the thing that makes builds repeatable.
- Using `pip install` without `--require-hashes` inside the Docker build, which trusts whatever the index serves.
- Mixing the project's `>=` ranges and the audit: audit the lock, not the ranges.

## Check yourself

1. What is the difference between `pyproject.toml` dependencies and the lock file?
   *Ranges the project accepts versus the exact versions and file hashes actually installed.*
2. What does `--require-hashes` guarantee?
   *Every installed file matches a hash recorded in the lock; unpinned or unhashed requirements are refused.*
3. Why `--no-deps` when installing the project itself?
   *The dependencies are already installed from the lock; no new resolution should happen.*
4. Why does the Dockerfile copy the lock before the source?
   *So the slow dependency layer is cached until the lock changes.*
5. What does `-e` mean?
   *Editable: the installed package points at the source folder.*
